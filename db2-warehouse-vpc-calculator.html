Production Primary / Live ▶
Production is the baseline. All other environments are sized as a % of Production by default.
DR / Standby Default: 100% of Prod ▶
DR must mirror Production exactly to be a valid failover target. By default it uses 100% of Production VPCs. You can reduce this if you use a warm/cold standby strategy.
UAT Default: 50% of Prod ▶
UAT simulates realistic user load for acceptance testing. Typically needs 50% of Production resources to replicate performance-sensitive test scenarios.
Test Default: 30% of Prod ▶
Test environments run functional and regression tests. They typically use a small data subset and low concurrency — 30% of Production is a standard IBM recommendation.
Development Default: 20% of Prod ▶
Dev environments are used by individual developers and rarely run concurrent workloads. 20% of Production is a typical IBM minimum to keep the environment functional without over-licensing.

Production Build-up (step by step)
A VPC (Virtual Processor Core) is IBM's software licensing unit for Db2 Warehouse. It maps to a physical processor core — not a logical thread. The calculation below builds up the required VPC count step by step, starting from raw data volume and layering on workload, users, features, and environments. Every factor has a documented IBM sizing rationale.
1
Base VPC from Data Volume
Base VPC = max(4, ceil(Database Size GB ÷ 500))
IBM Db2 Warehouse applies roughly 2:1 data compression for warehouse workloads. Every ~500 GB of raw data needs approximately 1 VPC of compute to handle scans, joins, and aggregation efficiently. The hard floor of 4 VPCs is the IBM-documented minimum for any Db2 Warehouse deployment.
2
Concurrent User Scaling
User VPC = ceil(Concurrent Users ÷ 10)
Db2 Warehouse's query scheduler assigns CPU slots per active query. At steady state, roughly 10 concurrent users share 1 VPC without significant queuing. Beyond this ratio, query wait times increase noticeably. This adds VPCs on top of the storage-based base.
3
Query Throughput (QPS)
QPS VPC = ceil(Queries/sec ÷ (5 × Storage Factor))
A single VPC can sustain roughly 5 queries/second on NVMe storage. This drops to ~3.75 q/s on SATA SSD (×0.75) and ~2.25 q/s on spinning HDD (×0.45), because I/O bottlenecks become the constraint. If you entered hardware specs, the storage type you selected adjusts this baseline automatically.
4
Data Growth & Ingest VPC
Growth VPC = ceil((Daily Ingest GB × 30 × Retention Months) ÷ 2000)
ETL/ELT pipelines and continuous data loading consume CPU separately from query workloads. Every 2,000 GB of projected total data growth requires roughly 1 additional VPC to keep ingest pipelines from competing with query resources. This projects storage growth over the full retention window you entered.
5
Workload Type Multiplier
After Workload = ceil(Subtotal × Multiplier)
Different workloads have fundamentally different CPU profiles:
• OLTP (×1.0) — short, indexed row lookups; low CPU per query.
• Mixed HTAP (×1.3) — mix of transactions and analytics; both CPU and I/O compete.
• OLAP/DW (×1.5) — full scans, large aggregations, complex joins; highest CPU demand per VPC.
This multiplier is applied to the combined subtotal from steps 1–4.
6
High Availability & DR Overhead
HA/DR Add = ceil(After Workload × 0.20)
IBM Db2 HADR (High Availability Disaster Recovery) runs a continuous log shipping and synchronization process on the primary node. This background workload consumes ~20% of the primary CPU budget on average and must be factored in to avoid degraded query performance during HA activity.
7
AI / ML Feature Overhead
AI/ML Add = ceil(After Workload × 0.15)
Db2 Warehouse's in-database AI features — vector search, automated statistics, ML model scoring — run inside the engine. When enabled, they add a background CPU footprint of approximately 15% over standard query processing, as they must co-exist with live query workloads.
8
Security Feature Overhead
Security Add = ceil(After Workload × 0.05 × Active Features)
Each active security feature (encryption, auditing, data masking, RBAC) adds ~5% CPU overhead. Encryption affects every I/O path; auditing writes to event streams; masking applies CPU-intensive transformations at read time; RBAC evaluates policy on every query. The overheads are additive (only applied when 2+ features are selected).
9
Platform / Virtualisation Overhead
OpenShift: +10%  |  VMware: +8%
Container and hypervisor layers introduce scheduling latency and memory overhead. OpenShift (OCP) adds ~10% due to pod scheduling, cgroups limits, and overlay networking. VMware adds ~8% from the hypervisor scheduler and memory balloon driver. Bare metal has no overhead. These are applied to the post-workload total.
10
Non-Production Environment Scaling
DR = 100%  |  UAT = 50%  |  Test = 30%  |  Dev = 20% of Production
Non-production environments need their own licensed VPCs. DR/Standby must mirror production exactly (100%) for a true failover target. UAT needs enough to simulate realistic load (50%). Test and Dev environments handle reduced concurrency and smaller data subsets, so 30% and 20% of production sizing are accepted IBM best-practice minimums.
11
4-VPC Tier Alignment
Final VPC = ceil(Total ÷ 4) × 4
IBM Db2 Warehouse is licensed and provisioned in increments of 4 VPCs (one standard node tier on IBM Cloud / Cloud Pak for Data). The total is rounded up to the nearest multiple of 4 to ensure you are purchasing a valid license tier — fractional tiers do not exist.
